# ddiv

Find an input that makes two C programs behave differently, and show the input
and both post-states. Each source already contains a `main` that calls the
function being tested. The framework is Python, with a small C runtime linked
into the tested programs to capture their state.

```sh
python -m pip install .
docker build -t ddiv:0.1 ddiv
ddiv 1.c 2.c
```

From this repository, `python -m ddiv 1.c 2.c` also works without installation.
This repository is a standalone Python project: it does not import
VanishBench, require benchmark bundles, or call any model.

## Example

```sh
ddiv ddiv/examples/1.c ddiv/examples/2.c --seconds 5 --output /tmp/ddiv-example
```

The example differs on `42`: the first program prints `84` and leaves the
global `answer` equal to 84; the second prints `85` and leaves `answer` equal to
85. The result includes a concrete input file, channel names, process outcomes,
and values from each program. An output directory must be new; previous results
are never overwritten.

```text
result.json                 complete result and provenance
config.json                 arguments, source hashes, Docker image ID
sources/{left,right}.c      exact supplied C source bytes
tool/                       Python/C implementation snapshot used for this run
build/                      compiler commands, logs, binaries, global layouts
afl.log, afl/               AFL++ log, queue, crashes, hangs, statistics
corpus/, corpus.json        frozen inputs, hashes, source of each input
replay.jsonl                completed comparisons before a counterexample
counterexample/input        exact distinguishing bytes
counterexample/left.json    first program's post-state
counterexample/right.json   second program's post-state
counterexample/difference.json
counterexample/{left,right}/{clean,sanitized}/
                            raw stdout, stderr, sanitizer logs, dumps, files
```

The default output directory is `./ddiv-results/<unique-run-id>`. Text output
previews long byte strings; JSON records full-content hashes and raw artifact
files preserve the complete counterexample observations. `--json` prints the
machine-readable result.

## Input generation and delivery

**AFL++ generates inputs**, using the first program as the reference. Its seed
defaults to 1337, and its time budget defaults to 60 seconds. An initial set of
text and binary boundary values starts the run. Use domain-specific seeds for
parsers that expect a structured format:

```sh
ddiv 1.c 2.c --seeds seeds/ --seconds 300
```

AFL++ runs once. Its queue, crash inputs, hang inputs, and initial seeds are
deduplicated and frozen; exactly the same bytes are replayed on both programs.
The frozen corpus and image ID support replay. A fixed RNG seed and time budget
do not guarantee byte-identical regeneration across different machines or loads.
Only retained queue/crash/hang inputs are replayed; AFL++ may discard mutations
that change a value without changing coverage. This is the same corpus boundary
as the existing oracle. Good seeds matter for such functions.

By default `main` reads the generated bytes from **stdin**, with EOF after the
input. Other main harnesses can use:

```sh
# fopen(argv[1], "rb")
ddiv 1.c 2.c --input-mode file

# main receives --input /tmp/ddiv/input
ddiv 1.c 2.c --input-mode file --arg=--input --arg=@@

# Generated bytes are a NUL-separated list of command-line arguments.
# The same small adapter handles AFL++ and replay, without invoking a shell.
ddiv 1.c 2.c --input-mode argv
```

In argv mode an empty file supplies no arguments; a trailing NUL terminates the
last argument. `--arg` adds fixed arguments before the generated arguments.
Stdin is consumed by that adapter. In file mode, `@@` is substituted wherever it
appears in a fixed argument; with no `@@`, the input path is the first argument.

Replay a saved counterexample without running AFL++:

```sh
ddiv 1.c 2.c --input previous-run/counterexample/input
# Replay an entire frozen corpus:
ddiv 1.c 2.c --seeds previous-run/corpus --seconds 0
```

## Post-state: adapted from the existing VanishBench code

This generalizes the existing [VanishBench](https://github.com/changliu98/vanishbench)
oracle to arbitrary main programs. Existing-implementation paths in this table
refer to that project:

| Component | Existing implementation | ddiv implementation |
|---|---|---|
| Two builds | `functional.py`, `difffuzz_run_v3.py` | `engine.py:build` |
| Normal-exit `.data/.bss` dump | V3 `instrument_custom_harness`, `_BB_BLOCK` | `runtime/state.c` |
| Compare by symbol name | `functional.symbol_digests_from`, V3 `symbol_digests` | `state.symbol_states` |
| Mask relocation slots | `functional.relocated_windows`, V3 `relocated_windows` | `state.elf_layout` |
| File observations | V3 `_filesystem_observation` | `state.filesystem` |
| Weakness + location | `crashparse.patterns_match`, V3 `crash_signature` | `state.crash_signature` |
| Repeat both programs | V3 `_stable_both`, `_dump_stable` | `engine.confirm` |

Each program gets an **ASan + UBSan build** for faults and a separate **clean
build** for memory. Both use `-O0` and the Clang version used by the installed
AFL++ compiler wrapper. The clean build's constructor registers an
exit handler that dumps `[__data_start, _edata)` and `[__bss_start, _end)`, just
as the existing custom-harness observer does. It does not rewrite `main`, repeat
the function under test, or alter the user's source file. ASan redzones are never
read by this dump.

Python compares:

- Exit codes, signals, timeouts, and sanitizer fault kind + read/write direction
  + faulting function. Source lines, columns and addresses are not crash identity.
- Exact stdout and stderr bytes from normal completions, separately for each
  build. Output addresses are not silently normalized away.
- Final files, directories, modes and symlinks under a fresh working directory.
  Each execution starts from the same empty directory, with the same input path.
- Writable `.data/.bss` symbols defined in the user's source object, matched by
  name. This excludes ddiv and compiler runtime globals and ignores linker padding
  and symbol order. A missing/added named symbol or changed size is a state change.
  As in VanishBench, load-time relocation slots are masked. Their ranges and raw
  bytes remain in the report. Empty global maps are valid; truncated dumps are not.
- Explicitly exposed local values and buffer contents, when supplied below.

A differing channel must reproduce on **both programs on four additional runs**,
followed by the archived witness run. Flaky differences are unresolved. This is
a finite determinism check, not a guarantee about every future execution.

The existing functional harness folds return values and output buffers into
`vb_digest`. An arbitrary `main` has no such harness-specific digest. Return
values discarded by main, locals that have gone out of scope, arbitrary heap
contents, registers, thread-local storage and masked pointer targets cannot be
recovered by a global dump. Make the relevant state observable in main by printing
it, storing it in a global, or using the optional helper:

```c
#include <ddiv.h>
/* ... inside main, after calling the tested function ... */
DDIV_OBSERVE("return_value", result);
ddiv_observe("output_buffer", buffer, initialized_length);
```

The last observation with a name is compared byte-for-byte. Observe initialized
values, not pointer addresses or uninitialized structure padding. Observation
calls also work in existing harnesses; the header is on ddiv's include path.

## Results and limits

| Result | Exit code | Meaning |
|---|---|---|
| `DIFFERENT` | 1 | A saved input has a confirmed observable difference |
| `NO_DIFFERENCE_FOUND` | 0 | Every frozen input was compared without a difference |
| `INCONCLUSIVE` | 2 | Flaky/missing observations, timeouts on both sides, incomplete replay, or failed fuzzing |
| `BUILD_FAILED` | 2 | One of the required builds failed; compiler logs are retained |
| `INFRA` | 2 | Docker/toolchain failure or interrupted run |

`NO_DIFFERENCE_FOUND` is bounded to this corpus and these observation channels;
it is not a proof of equivalence. A timeout difference means one program exceeded
the configured execution budget, not proven infinite execution. Use `--timeout`
and `--replay-seconds` for slower harnesses. If AFL++ cannot start (for example,
all seeds crash), seed replay can still produce a valid counterexample; otherwise
the result is `INCONCLUSIVE`, with the fallback recorded.

Memory capture currently targets Linux x86-64 ELF. `_exit`, `_Exit`, fatal signals
and hangs bypass normal-exit global capture. Raw mutable pointer values can be
nondeterministic; masked relocation slots deliberately do not compare pointer
targets. Heap effects need explicit observations, as they do in the benchmark's
generated harness. C undefined behavior is diagnostic evidence, not a meaningful
claim of language-level equivalence.

The input sources should be self-contained C translation units with main. Quoted
headers next to each source are available through a read-only mount; supplied C
bytes are frozen, but external header/library trees must be retained separately
for exact rebuilds. Additional flags use `--cflag=-DMODE=1` or `--ldflag=-lz`;
paths in flags refer to the container. Toolchain flags, sanitizers and architecture
are controlled by ddiv. `--image` / `DDIV_IMAGE` selects another compatible image
(the existing `difffuzz-oracle:22.04` and `vanishbench-cvf-afl:22.04` work).

All compilation, ELF inspection, fuzzing and target execution happens in Docker,
with network disabled, resource limits, a read-only root filesystem and read-only
source mounts. Cancellation removes only the container created by this invocation.
Files outside the execution working directory and interactions with external
services are outside the observation contract.

## Validation

```sh
python -m pytest -q ddiv/tests
DDIV_E2E=1 python -m pytest -q ddiv/tests
```

The first command checks the Python comparison logic. The second also builds and
runs real programs in Docker, including actual AFL++ generation. Set `DDIV_IMAGE`
to choose an already available compatible image for the Docker tests.
